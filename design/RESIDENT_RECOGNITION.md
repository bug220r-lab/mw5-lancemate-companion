# Private resident recognition component

Prepared September 23, 2026. **Project interface; native execution NOT_PERFORMED at preparation.** This is a frozen preparation record; any later execution has its own result receipt. This is independent local speech work under the full delivery plan. It does not change MW5, the observer, conversation models or the existing cold-recognition default.

## Concrete gap and supported route

The [six-clip resident Whisper benchmark](WARM_WHISPER_BENCHMARK.md) retained a model and observed lower component timings, but the unmodified HTTP server lacked a verified authentication gate and exposed unnecessary routes. The [cold-file adapter](LOCAL_RECOGNITION.md) was a deliberate baseline, not a rejection of retained model state. Its real two-word smoke took 2.179 seconds. Neither result satisfies human recognition, microphone or game-loaded acceptance.

The already installed, pinned CPU release contains `whisper.dll`. The [static source receipt](../research/RESIDENT_RECOGNITION_SOURCE.json) records the exact b5130 commit, header/license identities and required exports in the installed AMD64 binary. The [official C interface](https://github.com/ggml-org/whisper.cpp/blob/927cfce34f31707e17f2bff35c349632fb9e2c3a/include/whisper.h) exposes context creation, complete transcription, segment access and corresponding releases. Its parameter structs must match the exact binary ABI; an export name alone cannot prove compatibility. No extra package, public listener or new model is proposed.

The worker is project-authored Python using standard-library ctypes in an owned process. The independent header-derived Windows x64 expectations are 48-byte context parameters and 304-byte transcription parameters, both aligned to eight bytes. Complete fields and callback signatures are reviewed; a future native run must still establish actual invocation. A PATH check found no native compiler, which is not a machine-wide inventory or compiler-generated layout proof.

The exact upstream CLI explicitly registers backends before context creation (`examples/cli/cli.cpp:971,1081`). The worker must similarly call the declared `ggml_backend_load_all_from_path` with the verified runtime directory, then verify that the CPU device exists. Source review found that this function still honors `GGML_BACKEND_PATH`; both parent and worker remove that inherited override. Its Windows implementation uses ordinary `LoadLibraryW` for CPU candidates, so the child first restricts dependency search with [SetDefaultDllDirectories](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-setdefaultdlldirectories), checks success, and adds the verified runtime directory. The exact 40-file inventory is checked before these calls. CPU selection may briefly load several pinned variants to score them. No manual backend unload is attempted; registration and library handles remain process-owned. Static export checks establish only that the required names exist.

## Interface and ownership

`createResidentRecognition()` provides the existing project recognizer methods: start, transcribe, stop, dispose and status. It is opt-in and is not wired into the workbench. Import and construction are inert. Only explicit start can launch the exact pinned worker through the existing pinned Python executable. The worker independently checks the pinned model/archive and every recorded runtime payload before loading its library. No request can choose a path, model, executable, parameter set or method to invoke.

Parent and child communicate only through inherited pipes. Version-one JSON lines admit a single request at a time and strictly increasing request IDs. Canonical mono 16 kHz PCM16 WAVs are copied, base64-encoded and bounded to 0.1–15 seconds. The child validates the bytes again. Frames are bounded to 650,000 bytes; response lines to 8,192 bytes and transcript UTF-8 to 4,096 bytes. Transcripts remain untrusted and cannot become commands or verified mission observations through this component.

One CPU context stays owned between requests. Each transcription obtains fresh native greedy-decoding parameters, uses four threads and English, and disables past-transcript context, translation, prompts and timestamp output. Other native decoding defaults remain intact. The old CLI/server strategy and defaults have not been established as equivalent; these choices make this a new component test, not a controlled comparison isolating the effect of model residency.

Native standard output is kept away from the protocol pipe, and logs are discarded/bounded. Fixed error codes contain no supplied audio, transcript, path or raw native diagnostic. A worker error ends the worker. An idle normal stop requests context release and closure. Cancellation, timeout, resource loss or failed graceful stop may terminate only the owned child. A kill request is not proof of closure. Pending preflight/process cleanup prevents a replacement worker until it actually drains. Disposal forbids restart.

Startup requires 3 GiB available RAM and 10 GiB free disk, retaining the existing recognition admission limits. While owned, a 250 ms RAM sampler requests cancellation below 2 GiB or on an unavailable reading. This is reactive and cannot guarantee a hard memory reservation. Startup has a 30-second limit, each response ten seconds, and stop confirmation three seconds. Responses and startup handshakes must also pass elapsed-time checks, even when a JavaScript timer callback is delayed.

## Prepared bounded native component experiment

Before execution, freeze/review the worker, parent, tests, exact source/input/runtime pins and experiment runner. Verify interpreter and model/runtime pins, resource admission, and absence of conflicting project workers. Do not use the microphone, speakers, network listener, game or editor. Source inspection and fake tests cannot be reported as native success.

The [independent worker review](../research/RESIDENT_RECOGNITION_WORKER_REVIEW.md) found no remaining source-level ABI or backend-registration blocker. Its reviewed worker identity is pinned by the parent. The [independent parent review](../research/RESIDENT_RECOGNITION_PARENT_REVIEW.md) separately covers injected process, timing and protocol failures. `scripts/Exercise-ResidentRecognition.mjs` defaults to an inert help result; `--check` performs read-only preparation and `--run` reserves a unique result receipt before the single experiment. The runner's mock checks and complete component regressions must pass before that native invocation.

The intended single experiment starts one context and transcribes the existing synthetic clips **VA-001, VA-006, VA-001**, in that order. Record each normalized transcript against its existing reference, elapsed times, the same owned PID, memory samples, and confirmed disposal. Repetition is a small check of repeated requests and request isolation, not a fresh accuracy evaluation or proof that no context can ever leak. Preserve all failures in a new exclusive receipt. Stop on a mismatch, unexpected output, resource/deadline failure, crash or unconfirmed cleanup; do not retry unchanged or weaken limits.

This proposed run's outcomes are component invocation, private transport and retained-worker behavior. Three synthetic requests cannot establish a latency percentile requirement, real microphone correctness, natural-speech accuracy, game performance or release acceptance. A passing smoke still requires a separate decision and regression review before workbench integration. Existing cold-recognition receipts and defaults remain available.
