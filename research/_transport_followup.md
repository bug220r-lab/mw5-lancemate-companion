# Native transport source audit — follow-up memo

Accessed **2026-09-20**. This is a bounded source inspection for integration into the project’s final research documents. **No source was executed, no DLL was built or installed, and no loader, game, editor, save, mod, or runtime setting was changed.** Plain source copies remain in `research/evidence/transport-source/`.

## Decision

**RESEARCHED CANDIDATE; NOT IMPLEMENTED OR RUNTIME-VERIFIED:** a small native UEVR plugin using the MIT SDK wrappers, a bounded local Windows named pipe, and validated engine-tick callbacks is a concrete source-level candidate for an inbound channel. It would be new code. The inspected MechShaker bridge already proves an outbound memory-mapped transport pattern in public MW5 mod source, but it contains **no inbound receiver, lancemate-order operation, stable actor identity, authority check, or accepted-order acknowledgement**.

**Reject direct adoption of MechShakerBridge as the command adapter.** Its relay event detour, hardcoded engine layout, unframed shared memory, and build deployment side effects add unnecessary prerequisites. A narrow adapter directly using SDK callbacks avoids copying those particular hooks; it does not remove the loader’s own runtime hooks, compatibility risk, or the need to identify and verify the MW5 command path. This audit supports keeping native integration as a conditional fallback while the parent investigates the narrower editor/Victory lead. It does not recommend installation now.

## What the existing producer actually does

T01 `OnInitialize` (64–87) retrieves player controller index 0, looks for `ControllerFeedbackComponent`, and hooks `OnTelemetry`. The failure log explicitly points to **MechShakerRelay**. `OnTelemetry` (89–95) treats frame locals as `EventData` and copies them to memory. These are observed source symbols, not claims that those objects are available in the user’s installed game without that mod.

The event payload (5–14) contains an integer event code, one further integer, and six floats. Its producer semantics are not defined here. The source does not identify these floats as position, heat, armor, target, current order, or pilot identity. **Do not promote them into a useful companion telemetry schema.** README descriptions of haptic telemetry do not supply missing field semantics.

`SetupMemoryMappedFile` (98–119) creates the hardcoded `MechShakerBridgeMemory` map with default security attributes. `WriteToSharedMemory` (122–134) copies data and changes plain counters without an explicit atomic/seqlock publication protocol. No inbound producer ownership, bounded command parsing, session identity, freshness, duplicate rejection, or response channel is present. It is an outbound precedent, not a bidirectional protocol to relabel.

There is also a narrow source-inferred lifecycle defect: destructor lines 47–52 sets `Running=false` before trying to publish the close event, while writer lines 122–124 immediately returns when not running. This was **not executed**. It demonstrates why disconnect handling cannot rely on the apparent close packet.

## Invocation and thread boundaries

T03 `UObject::process_event`, `call_function`, and `UFunction::call` are real APIs, not invented MW5 nodes. T06 forwards them immediately to underlying SDK object methods. They accept opaque parameter memory and return `void` through these wrappers. They do **not** schedule on the game thread, validate an MW5 order’s parameters, prove server authority, or acknowledge a lancemate’s acceptance. A native call returning normally supports only a dispatch diagnostic unless the actual game function supplies independently verified semantics.

T04 registers pre/post engine-tick callbacks after its `on_initialize` call. In T06 the plugin-initialization loop runs within `on_initialize_d3d_thread`. Therefore the existing bridge’s initialization is **not evidence of safe game-thread access**. Rendering callbacks are also not a substitute for validated engine callbacks.

T07 discovers and installs a hook for engine tick. In that hook, engine-thread jobs execute at 418, mod pre-tick callbacks at 438, original tick at 456, and mod post-tick callbacks at 476. T06 delivers plugin pre/post callbacks directly while holding a shared callback lock. This gives a specific intended dispatch location, contingent on successful tick-hook discovery in the exact game/runtime combination. Slow I/O or blocking waits inside the callback would stall game work. Callback-list mutation must also respect loader locking.

T02 directly patches a function pointer at hardcoded **`UFunction + 0xD8`** and defines a partial raw `FFrame` layout. It restores saved function pointers without checking whether another mod has since changed them. These facts make it unsuitable as a version-neutral example. T03 also exposes generic `UFunction::hook_ptr`; its presence alone does not prove compatibility or necessity for this adapter. The proposed transport should require no MechShaker event detour.

## Proposed narrow adapter, contingent on later authorization

This is a design inference from T03/T04/T06/T07/T10, not code already present:

`local companion -> bounded named-pipe request -> plain-data queue -> verified game-thread callback -> one allowlisted native operation -> observed native state -> result queue -> companion`

Use explicit schema/version, mission epoch, command ID, expiry, one chosen lancemate identity, one supported order, and bounded payload/queue sizes. A transport receipt means only receipt. Keep separate validated/rejected/dispatched/observed-accepted states, with unknown/time-out outcomes never upgraded to success. Resolve game objects anew against the current world; do not send raw object pointers to the companion or hold them across mission epochs. Recheck identity, authority and manual-override cancellation immediately before dispatch.

A Windows named pipe provides a concrete duplex ingress candidate with overlapped I/O, remote-client rejection, an explicit access descriptor, and first-instance collision checks. For this project, scope its DACL to the intended local logon and validate the session handshake. These are proposed controls, not properties of MechShaker’s existing shared memory. Microsoft specifically distinguishes overlapped I/O from legacy `PIPE_NOWAIT`; the latter is not the asynchronous design to copy. Kernel32/Windows SDK supply the transport primitives. No web listener is required. [T10]

I/O parsing and waiting belong outside engine callbacks. A fixed worker/queue design is only acceptable after shutdown is solved: T06 removes callbacks and calls `FreeLibrary`, while T04 has no explicit pre-unload handshake. An independent worker must be quiescent before code is unloaded. Waiting for a worker in `DllMain` can deadlock under loader lock. A correct design needs an explicit pre-unload stop/cancel/drain protocol and supported loader coordination; “join it in the destructor” is not evidence this is safe. Disallowing hot reload in a test plan helps only if enforced by the runtime integration. [T04, T06, T11]

## Concrete prerequisites and stage gates

1. **Distribution and ABI gate — unresolved.** Select a legitimately usable runtime release and record binary origin/hash/version; check release terms separately. The inspected upstream root LICENSE says **ALL RIGHTS RESERVED**; only its SDK headers here are MIT. Do not describe the entire loader as MIT or assume redistribution permission. The loader checks required major/minor/patch versions (T06 1817–1838), but those checks do not establish game compatibility. MW5’s vendored 2.34.0 and inspected upstream 2.39.0 are distinct evidence pins.
2. **Build containment gate — unresolved.** Stock CMake has post-build PowerShell copying DLLs to `%APPDATA%/UnrealVRMod/MechWarrior-Win64-Shipping/plugins` (MechShaker lines 70–71 in `cmake.toml`, 445–446 generated CMake). A purported compile-only test of that project could deploy files. Remove deployment/bootstrap side effects in a project-contained build specification before any future build approval. No build was attempted.
3. **Dependency gate — unresolved.** Source targets C++23 and includes Windows/D3D headers, GLM, MinHook, and additional external include paths. MinHook source/include is referenced but absent from the inspected pinned tree; `.gitmodules` only declares GLM. `ext/openxr`/`ext/spdlog` paths are also listed without corresponding tree entries, though their actual need for the narrow bridge target requires checking. Do not call this a reproducible build. A new direct-SDK adapter could omit the custom hook/math/VR dependencies, but that is proposed implementation work.
4. **Lifetime/thread gate — unresolved.** Confirm tick callback delivery, thread identity, startup deferral, world transitions, shutdown, and unload without game orders first. The game receipt’s UE4 4.26.2 identity does not validate this loader’s dynamic hooks or raw layouts.
5. **Useful-state gate — unresolved.** Identify and read one real field with native semantics, freshness, invalid-state handling, and stable mission identity. A heartbeat or arbitrary float does not satisfy it.
6. **Command-path gate — unresolved.** Identify current MW5’s exact single-lancemate command operation, receiver, full parameter layout, local/host authority, and accepted-order readback. Reflection availability does not fill this gap. Co-op client dispatch remains blocked absent explicit authority evidence.
7. **Transport correctness gate — future isolated tests.** Exercise bounded malformed messages, expired commands, duplicate IDs, reconnect, stale epochs, disconnect during I/O, queue saturation, shutdown and command cancellation before a controlled native order trial. A local transport-only harness can test these later without pretending to prove MW5 integration.

**Claim boundary:** this audit narrows the engineering plan and exposes lifecycle/build/licensing constraints. It does not close the feasibility gap between receiving an instruction and one specific AI lancemate accepting a native command.
