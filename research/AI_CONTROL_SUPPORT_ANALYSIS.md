# Control, UI and supporting-source review

Reviewed 2026-09-21 UTC. OBSERVED exposed editor source/defaults for editor 1.1.390.0e, UE4.26.2; live use NOT_PERFORMED. **RUN** is [the verified collection](evidence/editor-source/ai-research-collection-20260921T030437Z-f7d8e930/report.json). Numbers below are asset IDs and one-based source line ranges. The coverage ledger supplies exact filenames and defaults citations.

This pass reuses the detailed [order lifecycle](ORDER_LIFECYCLE_TRACE.md) and [tactical state](TACTICAL_STATE_TRACE.md) traces, then examines registered UI/controller graphs and supporting libraries. Supporting-data review records a library's role and relevant paths; it is not a claim that every unrelated UI effect or generic utility has been exhaustively tested.

## Input becomes an order, not an acknowledgement

The base action 005 has an empty Initialize/Activate implementation and returns false from IsActionDisabled (204–251). Factory 006 constructs the chosen action, validates it, assigns OwnerMech and WorldContext, optionally calls Initialize, then returns the object (410–580). With deferred initialization, recipient fields can be assigned first. Base lance order 007 validates controller/order class, posts a Medium-priority nonpersistent order using the owner's command context, then immediately calls OnComplete (415–568). Its concrete descendants 000/242/245/247 select Follow/Attack/Move/HoldFire order classes in defaults. That UI completion remains distinct from native job acceptance.

Dispatcher 001 constructs page/slot actions, assigns recipient integers before initialization and uses member display IDs rather than the displayed lance index (3960–5169). A failed squad-info binding schedules a 0.2-second retry; Initialize separately updates display state (5647–5882). IsActionDisabled only tests recipient-array length (5170–5219), which cannot prove valid current AI ownership. SelectAll 246 and MoreCommands 244 construct directional layouts (129–411); their defaults select attack/move/follow and ECM/hold-fire respectively. Empty action 243 always reports disabled and its Activate callback carries a UI response only (37–72).

The older keyboard/joystick-style widget 008 is a separate source path. It binds dispatch inputs to DispatchOrder (1589–1764), selects recipients, then opens its order window (4767–5039). IssueOrderToRecipient posts the supplied order class through the local player controller with Medium/false-persistent context, then closes the window (4392–4490). Its order eligibility helpers inspect power/overheat/override/mission-complete state and display PlayerState/death information (5041–5307,5360–5462,5999–6130). These are UI-specific checks, not a replacement for current native identity/authority validation.

### New clarification: Cancel Orders here closes the menu

008 defaults line9 names `InputAction_CancelOrder="CancelOrders"`. UpdateBindings connects that variable to ListenForInputAction when the order window is open; its CreateDelegate explicitly selects **CloseOrderWindow** (4193–4214). That function sets bIsOrderWindowOpen=false, updates bindings and the widget switcher (4122–4166). It does not remove a worker, cancel a posting or finish a job. The earlier text search for the literal CancelOrders in source missed this indirection through the default field; this pass supersedes the blanket “no connected handler found” statement for this UI path. Other input paths or native cancellation remain unknown.

OnOrderIssued binds to IssueOrderToRecipient (4239–4258) and is removed on close/destruct (4267–4286,3273–3328). This is a concrete candidate for observing one UI submission path. It does not prove physical human origin: delegates/functions can be invoked programmatically, and other D-pad/controller paths must be covered. A complete manual-order observer is still unimplemented.

## Possession and component lifecycle

010 MW5PlayerController's HandlePawnPossessionChanged event calls OnPawnChanged (3575–3586 and2844–2854). The latter handles the new pawn's death state, and for a local controller updates input type then living/mech bindings (6580–6760). HandleMechBindings compares old/new references, unbinds old weapon/impulse/power/MASC/part events, binds the new ones, enumerates PlayerControllerComponent instances and calls ControllerConfigured with old/new pawns (4722–5426). A spectator branch has separate cleanup/configuration. These are source-backed invalidation leads; no runtime delivery guarantee has been measured.

The new-pawn IsValid node in HandleMechBindings has no invalid execution connection (5050–5059), so this function does not notify ControllerConfigured through that path for a null/unpossessed pawn. The spectator branch also depends on the multiplayer-client guard (4997–5005). This event chain alone cannot guarantee every transition is immediately invalidated; the observer needs independent current-binding checks.

AddPlayerControllerComponents queries assets of class PlayerControllerComponentDataAsset_C, checks bAddAtRuntime and whether the component class is already recorded, adds the component and finally calls ControllerConfigured on matching components (1444–1741). It first clears RuntimeControllerComponents (1456–1465); the Contains guard therefore deduplicates the current scan, not necessarily repeated invocations. **No connected caller of this function was established in this collection.** It is a candidate extension mechanism, not proven automatic mod registration or idempotent initialization. The base data asset 239 has ActorComponent=None and bAddAtRuntime=False. Base component 238 has an empty ControllerConfigured event and disconnected BeginPlay/Tick (20–64); default tick capability is false and autoactivation is false. A new component would need explicit lifecycle choices and a proven creation path.

011 forwards BeginPlay and construction to its parent; its Tick is disconnected (18–79). Its defaults choose UIScreensComponent and retain native components, including mission lifecycle and target visibility. Neither controller default `Role=Authority` nor the existence of a remote-control component establishes authority on a live instance or an available external command transport.

240 PlayerControllerSwitchMech receives ControllerConfigured, maintains the current player/mech references and supports SwitchMechInterface calls (2180–2210 and their connected gates). Selection checks include squad membership, living state and not-player-controlled status (1144–1164,1248–1298,1472–1564,1923–2003,2272–2433). The switch sequence handles weapon stop, movement stop, controller swaps, brain RestartLogic, cockpit/UI transitions and jump-jet override cleanup (1175–1183,1330–1347,1403–1452,1638–1771,1852–1881,2211–2262). This is a special possession transition, not a reusable complete piloting API.

The registered SwapControllers graph saves each pawn, excludes a dead target and ordinarily calls C1.Possess(LP2) then C2.Possess(LP1); spectators use a separate path (4307–4574). Its 0.5-second fade default is UI transition configuration, not measured control latency. 241 declares Switch Mech and ToggleSwitchMechAvailability interfaces (12–38) without implementing control itself.

## Order wrappers and utility boundaries

002/234/235 pass ExecuteOrder inputs into IssueOrder with Follow/Attack/GoTo jobs (18–41 each). 003 creates a constrained job posting and may remove workers from prior player-issued jobs; native selection/scheduling and acceptance remain missing (see existing lifecycle trace). 236 cycles each valid recipient's ECM component (36–153); 237 selects a shared interaction mode and applies it after a dialogue path (72–426). Neither is an idempotent desired-state command. 248 checks lance ECM availability during Initialize/UpdateState, using recipient values in an array-index calculation (1771–2049); its UI availability result must not be substituted for authoritative identity resolution. Activate still posts the configured native order (2050–2224).

232 GameplayTagLibrary supplies tag formatting/filtering, exact/wildcard match counting, footprint mapping and biome-role text (326–2111). CombatRolesToString extracts readable final tag segments (1856–2045); it does not select a mech's combat tactic. SafeTagContainerQuery rejects an empty container before applying a native tag query (1304–1374). No native tag implementation is recovered.

233 MacroLibrary supplies array/grid/map operations, debug flow, tag tests, random-selection helpers, formatting, role/persona handles and team-combat constants. Its IsOutOfRange macro computes the magnitude of actor-location difference and compares >= the provided range (4180–4280); no metres conversion is inserted there. Random-array helpers return index -1 for empty input (3351–3826,4021–4179). Persona macros return handles for later dialogue callers (6822–7087), not synthesized speech or conversations. TeamCombat limits are mode-specific constants (7315–7452), not proof of current encounter counts. Generic arithmetic/formatting and unrelated presentation are supporting data, not AI policy.

231 MW5_FunctionLibrary remains deliberately unexported due to the source-size budget. The connected AddUnitToSpawnQueue call in encounter logic is a specific remaining question; the missing body cannot be reconstructed from its signature.

## Consequence for the next observer

Use possession/configuration events as invalidation leads, not permanent slot bindings. Before any action, re-resolve squad member ID, controller, pawn, GUID and worker. Observe manual orders at their actual entry paths; menu closing, UI OnComplete and arrival dialogue cannot be promoted to order completion. A passive component is a plausible next experiment only after its actual creation/cooking path is established. All game-affecting steps remain NOT_PERFORMED.
