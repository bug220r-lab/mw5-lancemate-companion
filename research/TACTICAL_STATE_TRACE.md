# Tactical observation and current-control source trace

Accessed 2026-09-20 local time (collection directory timestamp 2026-09-21 UTC). **OBSERVED: offline source declarations and selected connected Blueprint pins. Live telemetry, adapter execution, command acceptance and shipping-game behavior: NOT_PERFORMED.**

The expanded collection supplies useful observation candidates for a tactical companion: current pawn/controller relationships, squad membership, health, armor, heat, ammunition, target visibility and navigation state. It does not supply a ready-made reliable snapshot. The most important newly documented constraint is that `MWSquadMemberDisplayInfo.squad_member_id` is explicitly **server only**. The most important control safeguard is a fresh, reciprocal pawn/controller binding with an explicit human-possession check immediately before any eventual dispatch.

Applicable source installation: Epic MW5 editor 1.1.390.0e, UE4.26.2 / compatible CL14830424. Retail Steam 1.14.390 / CL456620 compatibility is unproven. API text was inspected as text; its placeholder Python bodies (`return None`, `False`, zero and enum defaults) were not executed and are **not native implementations or observed runtime values**. C++ header names named by this generated reference do not imply the header bodies are supplied.

The older [telemetry audit](EDITOR_TELEMETRY_SOURCE_AUDIT.md) examined only binary strings. This trace supersedes its signature uncertainty for the concrete declarations below and its graph uncertainty for the specifically traced graphs. It does not establish their execution in a mission.

Three distinct evidence levels are used in the tables:

- **Declaration:** the generated reference exposes a named type/property/function and documentation.
- **Connected source:** selected exported graph pins connect the read to a consumer. This is source evidence, not a runtime trace.
- **UNKNOWN:** ownership, authority, freshness, replication, units or behavior still require validation. Read-only property flags do not establish thread safety or shipping availability.

**PROPOSED binding rule for the first proof:** select one controller from the verified player squad's current AI members. Obtain its current pawn and member display info; require reciprocal `pawn.get_controller() == controller`, no human possession, a live configured mech, a current valid server-side recipient ID, and that resolving exactly `[that_id]` through the real order resolver yields exactly that controller. Check both the designated AI and the order-instigator/follow-leader identities immediately before dispatch on the eventual authoritative game-side path. Unknown, missing, duplicate, switched or stale bindings must reject rather than guess. This rule is not implemented or tested.

The external process should not send raw UObject pointers or names as trusted identity. A mission/session identifier and actor/controller generations would be **project-defined** bindings maintained by a future adapter. Changing any binding invalidates outstanding intents. Equality checks sampled earlier in a mission cannot remove a later possession race; lifecycle events and dispatch-time revalidation remain required.

The later tactical layer can add per-part armor/structure, heat, ammo by unique bin, target identity/visibility history, combat range and navigation history. It should emit a small high-level choice with an explanation and confidence, then let the native AI aim, fire and move. It must not invent unavailable sensor observations. Real-time human-like play is the long-term user goal; these observations only narrow the feasibility work for live tactical decisions.
