# Direct-pilot aiming: input, state and ownership delta

Reviewed 2026-09-22. **OBSERVED:** preserved declarations; **DOCUMENTED:** the types/descriptions below. **UNKNOWN/BLOCKED:** native writers, consumption order, exclusive ownership and restoration. Native execution, game/editor launch, reflection import, control writes and deployment: **NOT_PERFORMED**. No adapter or simulated control result was created.

The useful new distinction is that desired arm/torso angles, current twist state, tuning limits/rates, replicated inputs and camera behavior are separate interfaces. An exposed angle-input structure is a credible investigation lead, but it is not proof that native AI will yield control or resume correctly.

## Actor overrides, camera controls and weapon identity

`MWMechAIController.set_torso_target_override(target_actor: Actor)` and `.set_arm_target_override(target_actor: Actor)` each return `None` (341509–341517, 341536–341544). Their descriptions merely repeat their names. The captured class has **no matching own getter/clear/release method** for these overrides. No priority, duration, nullable-reset semantics or preservation of previous intent is documented. Setting `None` must not be invented as an inverse. These actor-target requests also do not describe degrees, per-hardpoint pointing or low-level rotation ownership.

The same controller's `k2_face_target(Actor)` and `k2_face_location(Vector)` say they turn the **vehicle body** to face the target/location (341554–341571); they return `None`, not an arrival acknowledgment. `move_with_respect_to_combat_target` describes trying, where possible, to move along paths while facing the combat actor (341501–341508). These should remain separate from arm/torso-angle input. The inherited `MWMech.use_controller_rotation_pitch/roll/yaw` documentation applies when controlled by a **PlayerController** (340465–340467); it does not establish AI torso ownership.

`MWMechInputHandler` exposes only the battle-grid visibility delegate in its captured class (343609–343633), with a comment warning that its owner reference is unreliable. It supplies no exposed axis/torso setter here. This is a bound on this reference, not proof the native input handler has no internal methods.

`MWMech.mech_view_component` is a Read-Only component reference (340548–340552). The view component's writable relative transform, camera/boom fields and `cinematic_camera_look_vertical/roll/horizontal(float) -> None` (349413–349439) describe camera facilities, not a mech weapon actuator. Float input units/scaling are not specified. `center_legs(bool) -> None` likewise has only its name as description (349500–349508).

Free-look is especially unsuitable as an assumed reversible takeover shortcut: `enable_free_look()` explicitly **blocks toggling free look**, while `disable_free_look()` promises to unblock toggling but inconsistently describes itself as enabling free look (349338–349348). `is_free_looking() -> bool` (349305–349313) does not expose the prior toggle-lock state. The reference therefore does not establish that calling disable restores the prior configuration.

For observations, `MWMech.get_mech_aim_target_position(MechAimTarget, aim_assisted=False) -> Vector`, `get_aim_target_rotation(MechAimTarget) -> Rotator` and `get_aim_direction(MechAimTarget) -> Vector` are declared at 341229–341241 and 341263–341286. Units/frame, freshness, direction normalization and treatment of invalid targets are unspecified. `MechAimTarget` distinguishes `ARMS`, `TORSO`, `VIEW` (14141–14155); view direction must not be silently substituted for a particular barrel's direction.

The HUD weapon list/getter returns `MechHudWeaponEntry` (341242–341262). Its `weapon` reference, `aim_target` crosshair category, `aim_location` and `aim_obstructed` have Read-Only generated accessors (85823–85851), despite a Read-Write editor-property list (85781–85798). It is not a documented aiming setter. `AimObstructed` enum labels and adjacent comments disagree (15532–15534); do not turn this field into a proven clear-shot predicate without measurement. The already mapped weapon registry associates a weapon with aim category/mech part, and `MWWeaponComponent.get_weapon_hardpoint_slot_id() -> Name` (349789–349797) identifies a slot. None of these declarations proves per-hardpoint aim actuation, muzzle orientation, lock-on completion or an unobstructed firing solution.

## Ownership question and smallest next evidence

**UNKNOWN/BLOCKED:** which native writer produces torso/arm targets each frame, how those targets become replicated and actual joint/muzzle state, and whether any supported mechanism yields exclusive ownership while preserving a human command and the previous AI intent. `suppress_firing`, worker stop and brain restart do not answer this. Restoring an old angle/input snapshot after a target, pawn or ownership change could overwrite fresh intent; it is not a demonstrated restoration protocol.

**PROPOSED:** after passive-observer initialization and identity/freshness are established, first record native input/current-state/target values during ordinary target tracking and a player-requested possession transition, with an untouched sentinel and independently visible body/torso/arm movement. Treat event-only coverage and unavailable values as incomplete. Establish sign/frame, clamping, consumption order and which buffers change before considering an angle write. A later manifest-listed single-AI aiming experiment must have a documented writer-exclusion and restoration path, disposable Instant Action baseline, stop conditions and rollback. Camera movement, an override call returning, or animation change alone cannot satisfy that gate. No such experiment is implemented or run here.
