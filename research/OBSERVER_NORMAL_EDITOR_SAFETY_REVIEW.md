## Full-editor startup is a wider operation

The helper deliberately reads three registry referencer sets and writes project-local JSON. A full-editor startup additionally loads its default level, initializes plugins and can generate logs, caches, shader data, recovery/session information and editor configuration. The helper's no-load/no-save API scope does not apply to everything the engine does before Python starts or while exiting.

Before selecting an actual command, the plan needs a narrow read-only inventory of effective startup behavior: the selected project and default level; configured Python startup scripts and relevant Python search paths; any discoverable automatic initialization script such as `init_unreal.py`; enabled relevant editor plugins; and existing restore, source-control, mod-creation or conversion prompts. Record identified paths/hashes and uncertainty. Do not add startup scripts, edit settings, disable plugins, set up remote execution or invoke an unreviewed script to make startup succeed. This is a review requirement for the chosen startup route, not a claim that a particular automatic script is present.

The [post-install review](EDITOR_POSTINSTALL_REVIEW.md), section **Configuration evidence for startup writes**, records candidate installed/user/shared DDC graphs. The [commandlet review](OBSERVER_REFERENCE_COMMANDLET_REVIEW.md), section **What the previous attempt actually proves**, records an earlier writable user DDC. These historical observations do not settle the effective graph for the new run. Identify actual local/shared cache and config destinations before claiming isolated writes. Record relevant named config fingerprints before and after; do not copy or restore whole profile/config/cache trees or erase shared data as rollback.

A normal close without a save prompt is useful evidence, but fresh preflight must still fail closed if an existing editor, commandlet, game test, helper lock or unresolved recovery state conflicts with the experiment. A new process must not attach to or close an existing editor to obtain its session. A restore/save/discard/conversion dialog is a stop condition; no silent prompt acceptance, asset save or discard is part of this experiment. Preserve any human work and report the unresolved state.

## Process ownership, resource monitor and shutdown

**PROPOSED minimum supervisor contract:**

1. Immediately before launch, record UTC time, a monotonic deadline origin, fresh RAM/commit/disk values, relevant process inventory and helper/target/executable/project identities. Require two passing admission samples at least one second apart, with the last at most two seconds old at launch. A missing or ambiguous path, process start time, resource sample or pin prevents launch. Record the exact working directory and argument vector; avoid a reconstructed shell string. Follow the Windows background-helper rule for launch visibility. Do not add speculative rendering, unattended, repair or prompt-suppression flags.
2. Launch exactly one owned editor process. Retain its process handle where supported and record PID, creation time, executable path, expected project/arguments and unique log path. Recheck identity before any stop action; a PID or process name alone is insufficient. Observe and record child PID, creation time, image path and parent relationship during the run. A later parent-PID match alone cannot establish ownership after PID reuse.
3. Monitor through the whole interval from process creation to confirmed exit, including startup before the helper is reached. Proposed stop floors are **2 GiB available physical RAM**, **2 GiB available commit** and **10 GiB free C: disk** for the current verified local destinations. If the startup audit identifies another writable volume or shared destination, revise its measurement/containment scope before launch. Observe every **250 ms**; a valid resource sample may be at most **two seconds old**, with a bounded sample timeout and no overlapping unbounded samplers. Missing/stale monitor data stops the experiment. Retain timeline samples at most **once per second**, capped at **1 MiB**. Sampling is cooperative and cannot guarantee that memory/disk never crosses a floor between samples.
4. Use the current proposed **300-second whole-process deadline** independently of the helper's **60-second cooperative lookup budget**. This replaces the original 600-second proposal after the autosave-default finding. The observed approximately 119-second initialization, five-second discovery delay and 60-second helper budget fit with margin; they do not guarantee completion in 300 seconds, and no helper wait/scan is added. The helper cannot preempt a stuck native call. On timeout, resource floor, user interruption, conflicting process, unexpected prompt or identity uncertainty, stop further work and attempt a normal close of the verified owned process. The proposed **30-second close grace is a maximum**, not an obligation to leave a rapidly deteriorating process running. State the exact escalation policy in the launcher design before implementation.
5. If owned-process termination becomes necessary, record why, the verified identity, termination method/result and remaining children. Only specifically observed and still identity-matched children may be cleaned up; no process-name sweep or guessed process tree. If identity cannot be re-established, do not kill an ambiguous process. Record `CLEANUP_UNKNOWN` and require owner intervention rather than claiming clean completion.

Successful automatic exit is an observation to verify, not an assumption derived from adjacent-engine documentation. A normal process exit or exit code zero does not mean Python ran, the helper succeeded, or a complete registry result was collected.

## Exact attempt and output attribution

The unchanged helper has no supervisor attempt ID or parent-process identity field. The supervisor must preserve attribution externally without modifying the helper:

- Create a unique **attempt directory** for the outer manifest, resource samples and dedicated logs. Record pre-existing direct-child `observer-references-*` directories and both observer lock states before launch. Mock fixtures under `observer-reference-helper-review-*` are excluded from native discovery.
- Use one unique absolute engine-log destination tied to the launched PID/start time, and capture the actual command line. Preserve startup/Python tracebacks and exit timing. Require the helper's printed `Observer reference lookup: <status> | <output_directory>` marker in that log to bind the exact completed output path; do not merely select the newest folder. Missing or conflicting attribution is `AMBIGUOUS_RECEIPT`, even if a plausible JSON file exists.
- After exit, require exactly one attributable new direct-child `observer-references-YYYYMMDDTHHMMSSZ-12hex` directory created within the recorded attempt interval. Cross-check its `output_directory`, script hash, three exact target paths/hashes, option values, classification and source-before/source-after evidence. Reject ambiguous concurrent output. Directory timestamps alone are not proof of process ownership; the dedicated log and single-process/exclusive-run record supply the additional attribution.
- Hash each actual JSON file, retain raw bytes unchanged, and distinguish started/checkpoint evidence from a valid final `report.json`. The unchanged report's `native_execution=ATTEMPTED` is its recorded field; the outer receipt may separately record verified native metadata collection only when the report and log support that conclusion. Keep process outcome, helper outcome and research conclusion separate.
- A preflight failure may produce no new directory. A resource stop, crash or JSON-write failure may leave only checkpoints. Classify the observed failure stage using retained logs and files; absence of a report is neither an empty reference result nor permission for an automatic rerun.

The helper's [preparation manifest](OBSERVER_REFERENCE_PREPARATION.json) gives a designed ceiling of **1,081,344 bytes** for started/checkpoint/final JSON, plus its temporary **32-byte lock**. This does not bound the engine log, outer resource ledger, crash artifacts, DDC or shader output. The current planned supervisor budgets are **64 MiB aggregate owned logs**, **1 MiB for the timeline at at most 1 Hz**, and **4 MiB aggregate outer JSON metadata including that timeline**, with stop-on-growth rather than truncation of another process's/shared log. Private baseline configuration copies have a separate **4 MiB ceiling**; if the exact required files exceed it, revise the manifest before launch. A unique attempt log is not permission to delete historical evidence. Cache growth is constrained only by observed disk floors and timely shutdown, not by these JSON/log ceilings.

Treat a leftover helper lock as evidence. Preserve its bytes/path and compare them with any token observed during the owned run. The helper removes only its own exact lock. After abnormal termination, do not automatically erase an unattributed or changed lock to permit another run; first establish ownership and absence of all relevant processes. Preserve partial outputs even when cleaning up an attributable stale lock later.

## Acceptance and rollback limits

**Acceptable research result:** a properly attributed, hashed native report with exact reviewed script/targets/options and interpreted loading/cap/error state. Positive package references are candidate leads. Empty/None/partial/loading/error results remain distinct, and a false loading flag is not an exhaustive-index guarantee. The known Instant Action parent relationship can be used as a source-backed diagnostic expectation without adding new scans; its presence would support that portion of the index, not prove universal completeness.

**Not established by this experiment:** connected factory invocation, automatic observer creation, cooked registry visibility, runtime ownership, telemetry, native control or retail compatibility. No helper success can make those milestones pass. No source exports, broad collector, asset authoring, Play/Simulate, save/compile/cook, deployment or campaign action should follow automatically.

Rollback for this proposal means verified process/owned-child exit, preserved evidence, no remaining attributable active helper, and comparison of named asset/config fingerprints. Record expected incidental cache/log/session changes separately from deliberate source/settings changes. Do not claim a pristine environment merely because the helper never called a save API. No general cache cleanup or shared-config restore is justified by this experiment.

**Review disposition:** the proposed gates, single-process ownership and bounded receipt review form a reasonable basis for a later experiment, provided the outstanding startup audit, exact launch recipe, supervisor implementation and evidence attribution are completed. **Current resource admission remains BLOCKED; launch, helper lookup and launcher validation are NOT_PERFORMED this turn.**
